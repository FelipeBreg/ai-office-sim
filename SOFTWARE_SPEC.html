The Critical Gap

The software has the body (UI, schemas, routers) but needs the heartbeat — the autonomous loop that makes agents wake up, check KPIs, trigger workflows, cascade to other agents, and keep the company running without human intervention. This specification defines exactly how that heartbeat works, drawing from proven patterns in autonomous agent architectures.

Key Architectural Insight

Autonomous agents are comprised of exactly four categories: (1) What triggers the agent, (2) What is injected on every turn, (3) What tools it can call, and (4) What it outputs. The agent runs in a loop — LLM calls a tool, gets feedback, decides next step — until the task is done. This is the harness. Learning to build the right harness for each agent type is what separates a demo from a production system.

5. THE AGENT HARNESS

The harness is the exoskeleton built around the LLM that gives it the capacity to perform complex tasks autonomously. Every agent in our system runs inside a harness. The harness handles four things: what wakes the agent up, what it knows when it wakes up, what it can do, and what it leaves behind.

Why this matters

A generalist agent (like OpenClaw) packs everything into one harness: browser control, terminal access, memory files, cron jobs, skills, plugins. After a month of use, it accumulates 45K+ tokens of context overhead before the user even sends a message, causing 40-90% performance degradation from context rot.

Our system uses sniper agents — each agent has a focused harness with only the context it needs. An SDR agent gets CRM tools and sales knowledge. A legal agent gets law references and document tools. This keeps context tight (~1-3K tokens of overhead) and performance high.

5.3 Zone 2 — Context Injection (What the Agent Knows)

On every agent execution, the harness builds a context window. The order and token budget of each layer matters critically for performance. Here is the injection stack, ordered by priority:

#LayerToken BudgetContentStatus
1 System Prompt (Soul) ~500-800 The agent's identity, role, personality, rules. Bilingual. Like OpenClaw's soul.md. DONE
2 Strategy Context ~200-400 Active company strategies + current KPI values. Injected so the agent makes strategy-aware decisions. Compact format: "Goal: X | KPI: Y at Z% of target" MISSING
3 Heartbeat Instructions ~100-300 Agent's self-written instructions for what to do on this heartbeat tick. Similar to OpenClaw's heartbeat.md — the agent can rewrite this to program its own future behavior. MISSING
4 Dynamic Memory ~300-600 Key-value pairs auto-extracted from previous sessions. Operational short-term memory. Like OpenClaw's memory.md. DONE
5 Session History ~500-1000 Compressed summaries of last N sessions. NOT raw conversation — summarized to key decisions, outcomes, and learnings. PARTIAL — loads last 5 summaries, no token cap
6 Tool Schemas ~400-800 JSON schemas for only the tools this agent has access to. NOT all 30+ tools — just the 3-8 tools assigned to this agent. DONE
7 Trigger Payload Variable Context from whatever triggered the agent: cron schedule info, KPI threshold data, agent message, webhook payload, user prompt. DONE

Target: ~2,000-4,000 tokens of fixed overhead per agent

This is 10-20x leaner than a generalist agent's 45K+ tokens. The key: each agent only gets what it needs. A legal agent doesn't get marketing tool schemas. A sales agent doesn't get devops context.

CRITICAL — Context Rot Prevention

If context injection is not token-budgeted, agents will gradually accumulate more memory, more session history, and more tool schemas until performance degrades. Every injection layer MUST have a hard token cap. When a layer exceeds its budget, it must be compacted (summarized into fewer tokens) or truncated (oldest entries dropped).

6.1 Approval Pause & Resume

When an agent hits a tool that requires approval:

  1. Serialize: The entire session state is captured as JSON — messages array, loop counter, safety counters, pending tool call arguments, cascade metadata.
  2. Store: Saved in the approvals table's sessionState JSONB column.
  3. Notify: Socket.IO event approval:requested → UI badge count updates → Atlas gets popup if user is chatting.
  4. Wait: Agent status set to awaiting_approval. The cascade branch is paused.
  5. Resume (Approve): Worker deserializes state, executes the approved tool, feeds result back to LLM, continues the agentic loop from where it left off.
  6. Resume (Reject): Worker deserializes state, injects a "tool was rejected by human" message, lets the LLM decide how to proceed (may try alternative approach or complete gracefully).

Status: DONE — This is fully implemented.

6.2 Approval Timeout & Expiry NEW

Approvals cannot wait forever. An agent stuck in awaiting_approval blocks its cascade branch and wastes a concurrency slot.

  • Default expiry: 48 hours (configurable per project: 1h-168h)
  • On expiry: Worker deserializes state, injects "Approval request expired after {hours}h — no human response. Proceed with an alternative approach or complete gracefully." Agent continues the agentic loop.
  • Countdown in UI: Approval cards show time remaining. Turns yellow at 25% remaining, red at 10%.
  • Notification escalation: At 50% expiry time, send reminder notification. At 90%, send urgent notification.
  • Event: Emit approval:expired with approval ID and agent context.
  • Orchestrator check: The 60s tick scans for expired approvals and processes them.

7. CONTEXT HYGIENE & COMPACTION

Lesson from OpenClaw — Context Rot Kills Performance

After a month of daily use, OpenClaw's fixed overhead grows from 7K to 45K+ tokens. Research shows this causes 40-90% performance degradation. The LLM literally gets worse at its job because it has too much to process. Every additional token in the context window slightly degrades attention to the tokens that matter.

7.1 Token Budget System NEW

Every context injection layer has a hard token budget. The harness enforces these limits before sending to the LLM.

LayerMax TokensWhen Over Budget
System Prompt 800 Never changes — fixed per archetype. Ensure prompts stay within budget at creation time.
Strategy Context 400 Truncate to top 3 strategies by priority. Only active strategies.
Heartbeat Instructions 300 Hard truncate. Agent must be concise when writing heartbeat instructions.
Dynamic Memory 600 Keep most recent N key-value pairs. Drop oldest entries.
Session History 1000 Compaction: If last 5 summaries exceed budget, re-summarize into fewer, more compressed summaries.
Tool Schemas 800 Only include tools assigned to this specific agent (3-8 tools, not all 30+).
Trigger Payload 500 Truncate large payloads. Summarize if needed.
Total Fixed Overhead ~4,400 max This leaves 95K+ tokens for the actual agentic loop on a 100K context model.

Token Counting Implementation NEW

Token budgets require actual token counting. The harness uses a two-tier approach:

  1. Fast estimate: Math.ceil(text.length / 4) — used for quick checks during context assembly. Accurate within ~10%.
  2. Exact count: Anthropic's count_tokens API endpoint — called once before the final LLM call to validate the assembled context is within budget.

Add a shared utility package: @ai-office/tokenizer exporting estimateTokens(text) and countTokensExact(messages). The exact count uses Anthropic's API (no third-party tokenizer dependency).

7.2 Compaction Engine NEW

Inspired by OpenClaw's compaction system. When context grows too large during a session, the harness compacts it.

In-Session Compaction:

  1. After each tool call, count total tokens in the messages array.
  2. If approaching 80% of the model's context window:
  3. Take the oldest N messages (keeping system prompt + last 3 exchanges).
  4. Summarize them via a fast model (Claude Haiku): "Summary of actions so far: [compact summary]"
  5. Replace the N messages with one summary message.
  6. Continue the agentic loop with the compacted context.

Cross-Session Compaction (Session History):

  1. Each completed session produces a summary (50-200 tokens).
  2. Load the last 5 summaries into next session's context.
  3. If 5 summaries exceed 1000 tokens, merge the oldest 3 into one super-summary.
  4. Result: always have recent detail + compressed older context.

Memory Compaction (Key-Value Pairs):

  1. Auto-extraction adds ~5-10 new key-value pairs per session.
  2. After 50+ pairs, run a merge: combine related pairs, drop stale entries.
  3. Cap at 30 most-relevant pairs per agent (rank by recency + access frequency).

9. SELF-PROGRAMMING AGENTS

The Most Powerful OpenClaw Pattern

OpenClaw's heartbeat fires every 30 minutes and tells the agent to check heartbeat.md. The key insight: the agent itself can write to heartbeat.md. So it effectively programs its own future behavior. An agent that finishes a research task can write "Tomorrow, check if the report was reviewed and follow up" — and its future self will see that instruction and act on it.

9.1 How Self-Programming Works in AI Office Sim NEW

Heartbeat Instructions Field

Heartbeat Execution Flow:

  1. Orchestrator tick (every 60s) checks all agents where heartbeatIntervalMin is set and isActive = true.
  2. For each agent where now - lastHeartbeatAt >= heartbeatIntervalMin:
  3. Enqueue an agent execution with trigger type heartbeat.
  4. The trigger payload includes: "Heartbeat check. Your instructions: {heartbeatInstructions}"
  5. The agent runs its normal agentic loop. During execution, it can call:
  6. update_my_heartbeat — rewrites its own heartbeatInstructions for the next tick.
  7. update_my_schedule — changes its own heartbeatIntervalMin or cron schedule.

9.2 Safety Guardrails for Self-Programming

  • Minimum interval: heartbeatIntervalMin cannot go below 5 minutes. Prevents runaway agents.
  • Instructions cap: heartbeatInstructions capped at 500 characters. Forces concise future-programming.
  • Budget still applies: Every heartbeat execution counts against the agent's daily budget. An agent that sets a 5-minute heartbeat will burn through budget fast — this is self-regulating.
  • Admin override: Users can always manually override heartbeat instructions and schedule from the agent config UI.
  • Heartbeat audit: Every heartbeat instruction change is logged to action_logs with actionType: 'self_program'.
  • Version history: Every instruction change is stored in agent_heartbeat_history table (id, agentId, instructions, previousInstructions, changedAt, changedBySessionId). Cap at last 20 entries per agent. UI shows diff between versions. Manual rollback button restores any previous version.
  • Rate limit: An agent can modify its own heartbeat instructions max 3 times per session. Prevents instruction thrashing.

11. AUTONOMOUS TRIGGER MODEL

11.1 The Cascade Pattern

How autonomous operation works:

  1. Entry point: A cron schedule fires, a heartbeat ticks, or a KPI threshold is crossed.
  2. First execution: The triggered agent runs its agentic loop. It performs tasks using tools.
  3. Side effects: The execution produces outputs — documents created, KPIs updated, events fired, agents messaged.
  4. Cascade: Those outputs trigger more agents/workflows:
    • A KPI update crosses another threshold → another agent/workflow triggers
    • A fired event matches a workflow's event trigger → that workflow runs
    • An agent uses trigger_agent → target agent wakes
    • A heartbeat agent writes new instructions → its future self acts differently
  5. Equilibrium: The cascade continues until no thresholds are crossed, no events need handling, and all heartbeat agents have checked in.
  6. Human checkpoints: At any point, an approval-required action pauses that cascade branch.

11.2 Cascade Safety NEW

Cascade Depth Tracking:

Every agent execution and workflow run carries cascade metadata:

interface CascadeContext {
  cascadeId: string;      // UUID of the original trigger event
  cascadeDepth: number;   // How many levels deep we are (starts at 0)
  cascadeRootType: string; // 'schedule' | 'kpi' | 'heartbeat' | 'manual' | 'webhook'
  cascadeRootAgentId?: string;  // The agent that started the cascade
  cascadePath: string[];  // Array of agent/workflow IDs in the chain
}

Safety Rules:

  • Max cascade depth: Configurable in orchestrator config (default: 5). When a trigger would create depth > max, it's rejected and logged.
  • Loop detection: If cascadePath contains the same agent/workflow ID twice, it's a loop. Reject and alert.
  • KPI cooldown: After a KPI triggers an action, that KPI cannot trigger again for triggerCooldownMin minutes (minimum 15).
  • Agent cooldown: An agent cannot be triggered more than N times per hour (configurable, default: 12). Prevents rapid-fire heartbeat abuse.
  • Budget circuit breaker: If total cascade cost exceeds a configurable threshold, halt the entire cascade and alert the user.
  • Rate limit on trigger_agent: Max 5 trigger_agent calls per agent per session. Prevents a single agent from spawning unlimited cascades.

Cascade Failure Recovery NEW v4

When an agent in a cascade fails:

  1. Retry: Per-agent retry policy (0-3 retries, exponential backoff: 10s, 30s, 90s).
  2. If retries exhausted: Mark this cascade branch as partial_failure. Log failure reason, agent ID, cascade depth.
  3. Other branches continue: A failure in one branch does NOT halt the entire cascade. Only the failed branch stops.
  4. Notify: Emit cascade:branch_failed event. Create Atlas alert: "Agent {name} failed in cascade {id} at depth {n}. Reason: {error}."
  5. Cascade status: Track overall cascade status: in_progress, completed, partial_failure, failed (all branches failed).
  6. UI: Cascade trace view shows failed branches in red with error details and a "Retry branch" button.

23.2 The Key Principle

Give each agent just enough context to operate well without giving it too much and causing context rot.

This means:

  • Each agent gets only the tools it needs (not all 30+)
  • Each agent's system prompt is focused on its role (not a generic "you can do anything")
  • Each agent's memory is scoped to its domain (not shared with every other agent)
  • Each agent's session history is compacted to stay within token budget
  • Strategy context is compact (goals + KPIs as numbers, not full strategy documents)
  • Static RAG is pre-filtered to the archetype's domain

The result: 55 agents that each perform at near-peak capability, versus 1 bloated agent that gets worse over time.

24. EXECUTION RISKS

RISK 1 — Infinite Cascade Loops

Agent A → Agent B → KPI update → triggers Agent A again. Fix: Cascade depth limit (max 5), loop detection via cascadePath, KPI cooldowns (min 15 min), per-agent hourly trigger cap.

RISK 2 — LLM Cost Explosion

Autonomous agents running 24/7 with heartbeats can accumulate costs rapidly. Fix: Daily budget per agent (exists), project spend cap (exists), cost estimation before agent creation (needed), hard stop at zero balance (needed).

RISK 3 — Heartbeat Runaway

An agent sets its heartbeat to 5 minutes and does expensive operations each time. Fix: Budget enforcement counts heartbeat costs. Agent auto-disables when budget runs out. Minimum interval of 5 minutes.

RISK 4 — Context Rot Over Time

Even with sniper agents, memory and session history grow. Fix: Token budget system with compaction engine. Hard caps on every injection layer. Periodic memory merging/cleanup.

RISK 5 — Agent Reliability at Scale

LLMs are probabilistic — 10% failure rate at scale means dozens of bad outputs daily. Fix: Approval system for high-risk actions, health monitoring with auto-disable, reviewer agents at end of workflows, confidence scoring.

RISK 6 — User Onboarding Complexity

24+ screens is overwhelming. Fix: Company templates (exists), Atlas-guided onboarding ("Tell me about your company"), guided setup flow to first autonomous workflow in 10 minutes.

25. DESIGN FLAWS & FIXES

Flaw 1: "Always-On" Has No Mechanism

triggerType: 'always_on' exists in schema but nothing implements it. LLMs are request/response — an agent can't truly run continuously.

Fix: "Always-on" = heartbeat every 5-15 minutes + event subscriptions. It's a UI preset combining frequent heartbeat with broad event triggers. No new enum value needed — it's a convenience shortcut in the agent config UI. The agent checks for work on each heartbeat and responds to events as they arrive.

Flaw 2: No Standard KPI → Trigger Path

Agents can't update KPIs, and KPIs can't trigger agents. The autonomous loop has no closing mechanism.

Fix: Add update_strategy_kpi tool + event-driven threshold check in tool + polling safety net in orchestrator tick + trigger config on KPIs.

Flaw 3: Dashboard Data is Isolated

Dashboard tables need data from external systems. No automatic sync.

Fix: Create scheduled "data sync" agents per integration (RD Station hourly, Meta Ads daily). This is the natural use case for cron triggers.

Flaw 4: Session Logs Not in Knowledge Graph

Action logs are in a separate table. Atlas can't RAG-search what agents did.

Fix: Post-execution, generate markdown session summary → wiki document → chunk + embed. Now Atlas can search past operations.

Flaw 5: No Cascade Depth Tracking

No metadata tracking cascade depth, making infinite loops possible.

Fix: CascadeContext metadata on every execution. Increment depth, check loop detection, enforce max depth.

Flaw 6: No Context Budget (OpenClaw Lesson)

Session history and memory load without token limits. Over time, this will cause context rot.

Fix: Token budget per context layer + compaction engine. Hard caps enforced before every LLM call. Use Anthropic's count_tokens API for exact validation.

Flaw 7: CEO Agent = Potential God-Agent v4

CEO Agent needs cross-cutting access (all KPIs, all agents, all strategies) which contradicts the sniper agent philosophy and risks context rot.

Fix: Two-pass triage. Claude Haiku scans a compact KPI snapshot (~500 tokens) first. Full CEO session (Opus) only runs when triage detects something requiring action. Most heartbeat cycles cost ~$0.001. See section 17.1b.

Flaw 8: No Approval Timeout v4

Agents requesting approval could wait forever if the user never responds, blocking cascade branches and concurrency slots indefinitely.

Fix: Configurable expiry (default 48h). Escalating notifications at 50% and 90%. On expiry, agent receives "expired" message and can try an alternative. See section 6.2.

Flaw 9: No Cascade Failure Recovery v4

When an agent fails mid-cascade, the entire cascade is undefined — no retry, no notification, no status tracking.

Fix: Per-agent retry policy (0-3, exponential backoff). Failed branches marked partial_failure, other branches continue. Atlas alert on failure. Cascade trace UI shows status. See section 11.2.

Flaw 10: Agent Auto-Disable Has No Recovery v4

Agents that hit 3 consecutive failures are disabled forever (until manual intervention). In a 24/7 system, transient API failures could disable half the fleet.

Fix: Cooldown state with exponential retry (1h → 4h → 24h). Auto-recovery health check. After 3 failed recoveries, create human task. See section 12.3.

Flaw 11: Session Summaries Pollute Agent Memory v4

Session summaries stored in agent_memory table compete with operational knowledge. Busy agents fill memory with summaries.

Fix: Dedicated agent_session_summaries table. Memory stays for operational k/v pairs only. See section 8.1.

Flaw 12: Single Worker = Single Point of Failure v4

One Render worker runs the entire autonomous system. If it goes down, all agents stop.

Fix: BullMQ competing consumers — deploy 2+ replicas with zero code changes. Leader election for orchestrator tick via Redis SET NX. See section 16.3.

28. GLOSSARY

TermDefinition
HarnessThe exoskeleton around an LLM that gives it triggers, context, tools, and output channels. Each agent runs inside a harness.
Agentic LoopThe core execution cycle: LLM → tool call → result → LLM → next tool call → ... → completion. The agent decides each step.
Sniper AgentA focused agent with minimal context overhead, specialized for one domain. Opposite of a generalist agent.
Context RotPerformance degradation caused by too much information in the LLM's context window. More tokens = less attention per token.
CompactionSummarizing old context into fewer tokens to stay within budget. Applied to session history, memory, and in-session messages.
HeartbeatA periodic timer that wakes an agent to check its self-written instructions and act. Enables self-programming behavior.
Self-ProgrammingAn agent's ability to write its own future instructions (heartbeat.md pattern). The agent decides what its future self should do.
CascadeA chain reaction where one agent's output triggers another. KPI update → threshold crossed → next agent triggers → more outputs → more triggers.
Cascade DepthHow many levels deep a chain of triggered executions has gone. Limited to prevent infinite loops.
Static RAGImmutable, platform-provided knowledge documents for an archetype's domain. The agent's "textbook."
Dynamic MemoryMutable key-value pairs auto-extracted from sessions. The agent's "personal notes."
Four ZonesThe framework: (1) What triggers the agent, (2) What's injected as context, (3) What tools it can call, (4) What it outputs.
CEO AgentA special system-level agent that reads company strategy, monitors KPIs, and orchestrates the agent fleet to reach the user's goals. Runs autonomously via heartbeat. The strategic brain of the company.
Daily BriefingA morning report generated by the CEO Agent summarizing KPI status, fleet health, actions taken, pending items, and recommendations. Surfaced to the user via Atlas.
Two-Pass TriageCEO Agent optimization: Claude Haiku scans a compact snapshot first (cheap). Only escalates to full Opus session when action is needed. Prevents god-agent bloat.
Cascade TraceA UI visualization showing the full chain of agents/workflows triggered in a cascade, with status, cost, and duration per node.
Approval ExpiryAutomatic timeout on pending approvals (default 48h). Prevents agents from being stuck indefinitely waiting for human response.
Auto-RecoveryAutomatic re-enablement of disabled agents after a cooldown period, using a health check execution to verify the agent works again.

29. ATTRIBUTION

The autonomous agent harness architecture in this specification draws significant inspiration from OpenClaw (ClawdBot), an open-source autonomous AI agent project. Key patterns adapted from OpenClaw:

  • Heartbeat timer — periodic agent wake-up mechanism
  • Self-programming — agents writing their own future instructions (heartbeat.md pattern)
  • Context rot — performance degradation from context window bloat, measured at 40-90% in production
  • Session persistence — JSONL transcript storage with compaction
  • Four categories of agent behavior — triggers, injection, tools, outputs
  • Memory extraction — post-session k/v pair extraction for operational memory

These patterns were adapted from a single-agent architecture to a multi-agent "sniper fleet" system with cascade execution, KPI-driven triggers, and fleet-wide orchestration — capabilities not present in the original OpenClaw design.
